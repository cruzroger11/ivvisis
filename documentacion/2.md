# Archivo 2: Aplicación de los Principios SOLID en IVVI S.A.

El desarrollo del sistema **IVVI S.A.** se ha regido por los principios **SOLID**, garantizando un código mantenible, flexible y con baja deuda técnica. A continuación, se detalla la implementación técnica y justificación de cada principio dentro del ecosistema del software.

---

## 1. Single Responsibility Principle (SRP - Responsabilidad Única)

**Definición:** Una clase o módulo debe tener una única razón para cambiar, centrando su funcionalidad en una sola tarea del dominio.

### Implementación en el Sistema
Se ha segregado la lógica de negocio de los controladores (rutas) mediante el uso de la clase **`InventarioService`**. 
*   **Ejemplo:** Anteriormente, las mermas se calculaban en la ruta de ventas. En la implementación actual, la ruta solo captura los datos y delega el cálculo y la afectación al servicio especializado.
*   **Justificación:** Esto asegura que si los criterios de auditoría industrial cambian, solo se deba modificar el servicio de inventario sin afectar el comportamiento de las interfaces de usuario o la lógica de compras.

---

## 2. Open/Closed Principle (OCP - Abierto/Cerrado)

**Definición:** Las entidades de software deben estar abiertas para su extensión, pero cerradas para su modificación.

### Implementación en el Sistema
Se utiliza la herencia de tablas unidas (Joined Table Inheritance) en los modelos de base de datos.
*   **Ejemplo:** La clase base **`Persona`** está cerrada para modificaciones estructurales, pero abierta para ser extendida mediante las subclases **`Usuario`**, **`Cliente`** y **`Empleado`**.
*   **Justificación:** Si en una fase futura se requiere añadir un nuevo tipo de entidad (ej. `ProveedoresInternacionales`), se crea una nueva clase que herede de `Persona` sin alterar el código existente que ya gestiona las relaciones básicas de nombres, teléfonos y direcciones.

---

## 3. Liskov Substitution Principle (LSP - Sustitución de Liskov)

**Definición:** Los objetos del sistema deben ser reemplazables por instancias de sus subclases sin alterar la corrección del programa.

### Implementación en el Sistema
El sistema de autenticación y perfiles trata a todas las especializaciones de `Persona` de manera uniforme en las vistas genéricas.
*   **Ejemplo:** Un método que espera una lista de `Persona` para generar un reporte de directorio puede recibir indistintamente objetos `Usuario` o `Cliente`.
*   **Justificación:** Al respetar las firmas de los métodos y el contrato de la clase base, garantizamos que el polimorfismo del sistema sea íntegro y no genere errores de tipo en tiempo de ejecución.

---

## 4. Interface Segregation Principle (ISP - Segregación de Interfaces)

**Definición:** Los clientes del software no deben ser obligados a depender de interfaces o métodos que no utilizan.

### Implementación en el Sistema
Aunque Flask no utiliza interfaces en el sentido estricto de lenguajes como Java o C#, el sistema aplica este principio mediante la **Modularización por Blueprints**.
*   **Ejemplo:** Las rutas de administración de usuarios están completamente segregadas de las rutas de operación de planta.
*   **Justificación:** Un operario de envasado no requiere cargar ni conocer los métodos de restablecimiento de contraseñas o auditoría de logs, reduciendo la exposición de funciones innecesarias y optimizando el acoplamiento del frontend.

---

## 5. Dependency Inversion Principle (DIP - Inversión de Dependencias)

**Definición:** Los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones.

### Implementación en el Sistema
Los controladores de alto nivel no instancian drivers de base de datos o utilerías de bajo nivel directamente, sino que dependen de abstracciones de servicios.
*   **Ejemplo:** El generador de facturas (`report_generator.py`) recibe objetos de datos genéricos y no se comunica directamente con los modelos SQL para su renderización.
*   **Justificación:** Esto permite que, si en el futuro se desea cambiar el motor de reportes de PDF a una API de impresión térmica, la lógica de ventas no necesite ser reescrita, ya que solo depende de la abstracción del servicio de generación.

---
**Conclusión:** La aplicación de SOLID en IVVI S.A. no es solo teórica; permite que el sistema pase de ser un software monolítico rígido a una plataforma modular preparada para el crecimiento industrial.
